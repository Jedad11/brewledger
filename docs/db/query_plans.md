# Reporting query plans (WBS 7.8)

Records `EXPLAIN (ANALYZE, BUFFERS)` output for every report query against
the WBS 7.8 performance fixture (`pnpm db:perf-seed`, generated by
`packages/db/perf-seed.ts`) — 6 months of a busy pilot store, NOT
`packages/db/seed.sql`'s tiny demo-cafe fixture. Budget: **2s p95 target**,
**3s CI-fail threshold** (`packages/db/tests/perf/report_query_performance.test.ts`).

**Adding a new report requires adding its plan to this document** — see the
WBS 7.8 Acceptance criteria.

## Status: measured for real (qa_engineer, 2026-08-22)

Docker/`supabase start` was reachable in the qa_engineer session that ran
this measurement (it was not in the engineer's authoring session — see
git history). Migration `0042` applied cleanly with no collisions,
`pnpm db:perf-seed` ran to completion, and the four WBS 7.1 queries were
measured with real `EXPLAIN (ANALYZE, BUFFERS)` below.

**IMPORTANT — run `ANALYZE orders; ANALYZE order_items;` after seeding.**
`perf-seed.ts` does not run `ANALYZE` itself, and immediately after a fresh
~11k/~26k row bulk load, autovacuum has not necessarily caught up. The first
measurement pass in this session, taken before an explicit `ANALYZE`, showed
`order_items`' planner row estimate off by ~40x (estimated 4287 rows vs. 104
actual) and produced a **Seq Scan on `order_items`** for the 7.1c query — a
false positive for a Seq Scan finding, not a real indexing gap: the covering
index resolved it as soon as statistics were current. Recorded below are the
post-`ANALYZE` plans. **Resolved:** `perf-seed.ts` now runs `ANALYZE` on all
six fixture tables (`orders`, `order_items`, `daily_financials`,
`stock_ledger`, `purchase_invoices`, `purchase_line_items`) at the end of
every run, so this is no longer a trap for the next person who runs it fresh.

**WBS 7.1b Seq Scans `orders` — resolved as a documented exception.**
See the 7.1b section below. This is a genuine, reproducible violation of the
literal acceptance line "No report query performs a sequential scan on
orders or order_items" at this fixture's data volume, even with correct
statistics and the 0042 partial index in place. Confirmed 3 times with
`set enable_seqscan = off` that the index-based plan is not actually faster
(3.88ms bitmap-heap-scan vs. 3.47ms seq scan) — the planner's choice is cost
correct at ~18% table selectivity on a table this physically small (fits in
a few hundred buffers). Both are far inside the 2s/3s budget, so there is no
user-visible performance problem.

**Orchestrator decision:** do not fight the planner or force the index (e.g.
`enable_seqscan = off`, an artificially degenerate index) — that would make
this query measurably slower for zero real benefit. Instead this is accepted
as a narrow, documented exception to the letter of the acceptance line.
`packages/db/tests/perf/report_query_performance.test.ts`'s WBS 7.1b test no
longer asserts `assertNoSeqScanOn` for this one query — every other query in
the file keeps the strict assertion. The `0042_reporting_indexes.sql` index
itself is untouched and still correct: it is what serves 7.1a, and it will
matter for 7.1b once a store's order volume grows enough that the matching
slice no longer fits in a handful of buffers (rule of thumb: re-test this
exception if daily order volume grows an order of magnitude from this
fixture's ~60 orders/day).

## WBS 7.1 — Dashboard summary (`fetchDashboardSummary.ts`, live at commit `cc91fb3`)

Four queries, run in parallel by `Promise.all` in the real code. Each needs
its own plan since Postgres plans them independently.

### 7.1a — Today's revenue orders

```sql
select id, total_satang, status from orders
where store_id = $1
  and status in ('ACCEPTED','PREPARING','READY','COLLECTED')
  and created_at >= $2 and created_at < $3;
```

Served by `orders_store_id_created_at_revenue_status_idx` (0042, partial on
the same status list).

```
Index Scan using orders_store_id_created_at_revenue_status_idx on orders
  (cost=0.29..96.34 rows=52 width=29) (actual time=0.042..0.057 rows=44 loops=1)
  Index Cond: ((store_id = $1) AND (created_at >= (now() - '1 day'::interval))
               AND (created_at < now()))
  Buffers: shared hit=20
Planning Time: 0.416 ms
Execution Time: 0.087 ms
```

Index Scan, no Seq Scan, 0.09ms. Well inside budget.

### 7.1b — Live working queue

```sql
select id, total_satang, status from orders
where store_id = $1
  and status in ('ACCEPTED','PREPARING','READY');
```

Served by `orders_store_id_created_at_idx` (0011) plus a status filter, or
`orders_store_id_created_at_revenue_status_idx` (0042) since
`{ACCEPTED,PREPARING,READY} ⊆ {ACCEPTED,PREPARING,READY,COLLECTED}` — the
planner picks whichever it estimates cheaper.

```
Seq Scan on orders  (cost=0.00..789.12 rows=2020 width=29)
  (actual time=0.595..3.407 rows=2020 loops=1)
  Filter: ((store_id = $1) AND (status = ANY ('{ACCEPTED,PREPARING,READY}'::text[])))
  Rows Removed by Filter: 8880
  Buffers: shared hit=612
Planning Time: 0.076 ms
Execution Time: 3.471 ms
```

**Measured Seq Scan on `orders`, post-`ANALYZE`, reproducible (3 runs).** At
this fixture's volume (10,900 orders/store, ~18% match the three working
statuses, table small enough to fit in a few hundred buffers), the planner
correctly costs a full scan cheaper than using the index — confirmed with
`set enable_seqscan = off`, which forces a Bitmap Heap Scan via
`orders_store_id_created_at_revenue_status_idx` at **3.88ms** vs. the seq
scan's **3.47ms**, i.e. the index plan is not actually faster here. Both are
far inside the 3s CI threshold and the 2s p95 target (3-4ms either way), so
there is no user-visible performance problem.

**Documented exception (orchestrator decision, see the Status note above).**
This is a literal violation of the WBS 7.8 acceptance line "No report query
performs a sequential scan on orders or order_items" as written, at this
fixture's realistic scale — not a false positive, not an artifact of stale
statistics. Forcing the index would make the query slower for no benefit, so
`report_query_performance.test.ts`'s WBS 7.1b test asserts only the timing
budget for this one query, not the absence of a Seq Scan; every other query
in the suite keeps the strict `assertNoSeqScanOn` check. Re-verify if a
store's daily order volume grows an order of magnitude past this fixture's
~60 orders/day — the index should start winning well before the table
outgrows a few hundred buffers.

### 7.1c — Order item cost rollup for today's revenue orders

```sql
select quantity, unit_price_snapshot_satang, unit_cost_snapshot_satang
from order_items where order_id = any($1::uuid[]);
```

Served by `order_items_order_id_covering_idx` (0042) — index-only scan
expected, no heap fetch for `quantity`/`unit_price_snapshot_satang`/
`unit_cost_snapshot_satang` since all three are in the `INCLUDE` list.

```
Index Only Scan using order_items_order_id_covering_idx on order_items
  (cost=0.29..182.36 rows=105 width=12) (actual time=0.039..0.188 rows=104 loops=1)
  Index Cond: (order_id = ANY ($1::uuid[]))   -- 44 order ids
  Heap Fetches: 0
  Buffers: shared hit=87
Planning Time: 0.690 ms
Execution Time: 0.220 ms
```

Index Only Scan confirmed, `Heap Fetches: 0` — the covering index does
exactly what it was built for. 0.22ms, well inside budget.

### 7.1d — Today's confirmed purchase invoice expenses

```sql
select total_satang from purchase_invoices
where store_id = $1 and review_status = 'confirmed' and invoice_date = $2;
```

Served by `purchase_invoices_store_id_idx` (0015) plus a filter — not a
report-query bottleneck (`purchase_invoices` is small relative to `orders`),
no new index added for this one.

```
Seq Scan on purchase_invoices  (cost=0.00..7.62 rows=1 width=4)
  (actual time=0.044..0.044 rows=0 loops=1)
  Filter: ((store_id = $1) AND (review_status = 'confirmed') AND (invoice_date = CURRENT_DATE))
  Rows Removed by Filter: 181
  Buffers: shared hit=4
Execution Time: 0.062 ms
```

Seq Scan, as expected and out of scope — `purchase_invoices` is not `orders`
or `order_items`, and the WBS 7.8 acceptance line only names those two
tables. 181 rows total for this store; 0.06ms. No action needed.

*(7.1's fifth query, upcoming pickup slots, reads `pickup_slots` and is
unrelated to the `orders`/`order_items` hot path this entry is scoped to —
tracked for completeness in `fetchDashboardSummary.ts` but out of WBS 7.8's
index scope.)*
